## 任务内容（与调度器 message 必须逐字一致）

```text
对 /workspace 的 TRAE-project 仓库做一次每日复盘（以分析为主，仅在需要补记账本或升级机制时改动文件）。步骤：1) 先按 AGENTS.md 的加载策略读 AGENTS.md、rules/00-core.md、rules/01-user-profile.md、rules/02-intake-and-dod.md，再读 PITFALLS.md；2) 用 git log 与 git diff 统计自上次复盘以来（默认最近 24 小时）的提交，找出返工、回滚、重复修改、被中断、反复沟通的事项；3) 检查 docs/handoff/CURRENT.md：用 git log -1 --format='%h %s' -- docs/handoff/CURRENT.md 与 HEAD 比对，若该文件落后于最后一次交付提交，按 rules/07 的交接快照节补记或标注"已过期，以 git log 为准"（ADR-013）；4) 不要只统计发生了什么，必须横向聚类分析共同根因（例如：机制只覆盖机械部分而聊天行为靠自觉、口径未确认就开工、同步失败、规则膨胀等）；5) 把可预防的共性根因落成防复发机制，优先级：自动检查脚本 > 模板/清单条目 > 规则文本；结论写回 /workspace/PITFALLS.md（新增条目或更新已有条目状态），同一条坑复发则按"复发即升级"升级；6) 输出简短复盘结论：本次聚类的共同根因、新增或升级的防复发机制、仍未关闭的待确认事项。若确实没有新问题，明确写"本日无新增坑"，不得编造问题。所有改动按 AGENTS.md 的交付反馈清单（D-1~D-7）汇报，并提交推送到 GitHub 后核对 ahead 0。
```

## 调度器重建步骤（实例丢失时按此恢复）

1. 按上表读取 cron 与时区，按本节代码块读取 message 原文；
2. 在调度器创建任务（参数：name、cron_expression、timezone、message）；
3. 把新任务 ID 回填到本文件「任务定义」表，并同步更新 `rules/06-quality.md` 中引用的任务 ID；
4. 提交推送，核对 `ahead 0`。

## 执行后验证（P-019，2026-11-19 起）

- **产物锚**：复盘完成以 **git 提交**为准——无新增坑也须提交一行复盘记录（例：`docs(retro): 2026-11-20 本日无新增坑`）；调度器 `Executions` 计数只说明"派发过"，不说明"完成了"。
- **每日首次会话核对**：首次会话先查调度器执行增量与 `git log` 是否对应；**有派发无提交 = 当日补跑**，并按 P-019 记入坑账本。
- 派发会话失败是静默的（无告警、无日志落库），不能假设"调度器 Active"等于"复盘在发生"。

## 降级方案（无调度器能力的环境）

- 外部 Agent（豆包、千问、DSH、WorkBuddy 等）若无定时调度：改为**每日首次会话开始时**执行同一份任务内容，并在输出中标明"降级执行：会话内触发"。
- 不得因为无法调度就静默跳过；无法执行必须在交付中写明原因与下次执行时间。
