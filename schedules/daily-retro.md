## 平台约束（2026-11-19 截图证实，不得假设相反）

- 调度器派发的是**全新沙箱**：`/workspace` 为空目录（无 `.git`、无 AGENTS.md、无 rules/）、`~/.ssh` 为空、`gh` 未登录、无任何凭据。派发会话**拿不到**主会话的工作区与密钥。
- 因此派发会话只能：匿名 clone 公开仓库 → 只读分析 → 把报告**输出在会话里**；它**永远无法 push**（无凭据，且凭据不得写进任务消息）。
- 落库（账本更新 + 提交推送）只能由主会话完成——见「执行后验证」的两层产物锚。
- 2026-11-19 00:00 的首次派发即因此失败：旧消息写"对 /workspace 的 TRAE-project 仓库"，新沙箱里该路径不存在，会话如实报"无法执行"（耗时 38s，未伪造提交、未建空仓库冒充——行为正确）。

4. 提交推送，核对 `ahead 0`。

## 执行后验证（P-019，2026-11-19 起）

- **产物锚分两层**：派发会话的产物 = 会话内完整复盘报告（无凭据沙箱的唯一合法产物）；主会话的产物 = **git 提交**（把派发报告的结论落成账本/机制更新，或主会话自行补跑）。调度器 `Executions` 计数只说明"派发过"，不说明"完成了"。
- **每日首次会话核对**：首次会话先查调度器执行增量与 `git log` 是否对应；**有派发无提交 = 当日补跑**（主会话执行完整复盘并落库），并按 P-019 记入坑账本。
- 派发会话失败是静默的（无告警、无日志落库），不能假设"调度器 Active"等于"复盘在发生"。

## 降级方案（无调度器能力的环境）

- 外部 Agent（豆包、千问、DSH、WorkBuddy 等）若无定时调度：改为**每日首次会话开始时**执行同一份任务内容，并在输出中标明"降级执行：会话内触发"。
- 不得因为无法调度就静默跳过；无法执行必须在交付中写明原因与下次执行时间。
