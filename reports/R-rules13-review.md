## 二、可执行性：`docs/CLAIMS.md`

事实：`docs/` 下只有 BACKLINKS.md、AGENT-ADAPTER.md、adr/，**无 CLAIMS.md**；README、AGENTS 索引均未登记该机制；`scripts/md_check.sh:55` 只校验 13 册是否含"认领"二字，不校验文件存在与格式。

已有（不算缺口）：
- 创建责任："该文件不存在时先创建"（13:7）——名义上有，但责任人不唯一（先到者），且无并发创建规则。
- 表头：`目标 | 认领人 | 认领时间 | 状态`（13:7）——仅字符串，无分隔行、无示例行。

缺失清单：
1. **格式细节**：Markdown 表格分隔行；"认领时间"格式与时区（本仓库统一 Asia/Shanghai）；"认领人"唯一标识；"状态"枚举（全文只出现"已完成"，未列"认领中/已释放"）。
2. **过期认领**：零条款。无 TTL、无心跳、无 Agent 崩溃/会话中断后的回收规则、无"由主 Agent 定期清理"的责任人与周期 → 一次异常退出即永久死锁。
3. **跨分支/跨机器次序**：git 同步存在延迟，两 Agent 各读旧表可同时认领；规则未要求"认领后先提交/先推送再开工"。
4. **与 08 的衔接**：CLAIMS.md 是否入库、何时提交、合并冲突时以谁为准，未写。
5. **注销形态**：13:9"释放"是删行还是留行改状态？删行与 AGENTS:46"审计资产永不删"冲突；留行则文件只增不减，无归档规则。
6. **目录 vs 文件优先级**（同可判定性第 4 条）。
7. **可发现性**：新接入 Agent 读不到 CLAIMS.md 就不会登记；需在 AGENTS 索引或 README 登记，并加机器校验（现无）。
8. **与 02 的顺序**：13:7"改任何文件前必须登记"而 02:7"边界未获确认前不得改文件"——登记本身算不算改文件、孰先孰后未写。

## 三、冲突与重复

**与 02（复述与边界）**
- 02:7"边界未获用户确认前，不得动笔、不得改文件、不得派发子 Agent" vs 13:7"改任何文件前必须……登记"：缺顺序声明，实操中会出现"先建 CLAIMS.md 还是先复述"的争议。
- 02:14 D-1（改 rules 须给全文）未在 13 承接（缺口，非矛盾）；02:19 D-6 与 13:17"写入待确认事项"重复，且 13 未要求 07:6 的四要素字段。

**与 04（派发与审查）**
- 实质矛盾：04:7/04:30"主 Agent 必须逐条审查……审查通过后才算真正交付" vs 13:9"自检通过后……释放"。按 13 释放后他人可合法接手并覆盖尚未审查的内容，审查窗口被架空。
- 规则打架：04:35"单一依据、版本冻结……不得自行填补……口径缺失就停下来问" vs 13:14"依次比对……不得越级各取所需"（赋予执行者自行按层级裁决的权力），而 13:16 又要求"停止改动"；同一人同一情形可得出相反动作。
- 04:44"留三件套审计"未覆盖认领记录的留存（13:9 处置方式未定）。

**与 06（任务分级）**
- 06:7"单个脚本或单份文档的修订一律属轻，不得升格套用重级流程"，06:8 例外仅限"规则条款"；13:21"按以下顺序执行，缺一步即未完成"（6 步）对**任何**功能/文档下线一律适用 → 单文档下线被强制升格，与 06:7 冲突。
- 06:36"重要决策写入 docs/adr/" vs 13:17"写入待确认事项**或** ADR"：13 允许二选一，等于给 ADR 开了豁免口。
- 06:12 定时任务仅授权"只读分析＋补记＋提交"，若需下线功能则 13 要求的改文档动作越权，13 未声明例外。

**与 08（提交推送）**
- 08:19"多 Agent 并行时必须按 13 册认领，**必要时开分支**"——13 全文无"分支"二字，无开分支条件、无 merge/rebase/冲突片段归属、无"合并后复检"；"必要时"的判定人未指定（08 指向 13，13 不接）→ 规则空转。
- 08:19"禁止对同一文件并行直推"与 13:8 重复，但层级不同（08 管 push，13 管改文件），13 无 push 层条款，两处口径不齐。
- 08:25-32 五步提交 vs 13:27"提交时说明影响面"：13 未指向 02 的 D-2/D-3，易被当成额外义务而非同一件事。

**与 01/07/11**
- 01:10"提问只问业务……技术选型、流程细节、文档形式一律由 Agent 自行决定"，13:16 却要求把"结论互相矛盾"（多数是文档/流程冲突）抛给用户；13 未区分业务冲突与技术冲突 → 可能直接违反 01 的硬约束。
- 07:8"用户是最终确认人；主 Agent 不能替用户默认确认" vs 13:10/13:17"交由主 Agent 裁决"且仅"留痕" → 裁决被当成默认确认，边界不清。
- 13:28"先按 11 留档，并由用户批准"：11 册无此条款（11 只要求改前备回滚），属失效引用。

## 四、裁决优先级是否自洽

11. **"显式规则"未定义**：是否含 AGENTS？含用户当轮口头指令？若用户当轮明确说"这次按 X"且与 ADR 冲突，按 13:14 应服从 ADR，这与 02:9"用户批准即直接执行"、01:5"业务口径以用户的专业判断为准"冲突。这会**误导**：Agent 可以拿 ADR 拒绝用户当轮的明确指令。
12. **ADR 的层位不稳**：ADR-002/005 本身就是新增规则的来源，内容已成"显式规则"；同一份文件既算 ADR 又算显式规则，归一档无法判定。
13. **"上位存在即按下位"**：把"矛盾才比"写成"存在即失效"，会消灭"默认惯例"的补充作用，并与 13:16"仍无法裁决"逻辑断裂（既然上位存在下位全废，何来"仍无法"）。
14. **同层"后发布优先"**：无发布时间口径，且与 AGENTS:73 的 BACKLINKS 自动生成冲突（13:17 要求"补反向链接"，脚本会重写该文件）。
15. **缺示例**：全节 0 个正反例，执行者无法把抽象层级套到具体场景；至少应给一正一反（如"05 要求政策条款" vs "任务口径称客户已认可" → 服从 05；"ADR 定的目录结构" vs "本次任务要求换目录" → 按 ADR 并提问）。

## 五、结论

**需小幅修订**（结构、六步退役主链可用；但认领一节若不补齐生命周期，等同该节需重写）。

必改项：
1. 补 CLAIMS 全生命周期：格式（含分隔行/时区/状态枚举/认领人标识）、目录 vs 文件优先级、TTL 与回收责任人、跨分支"先提交后开工"、注销是留行还是删行、入库与提交时机；并在 AGENTS 索引或 README 登记 + 加机器校验。
2. 定义"多个 Agent 同时作业"的触发条件；明确与 02 的顺序（复述→确认→认领→改文件）。
3. 13:9 改为"主 Agent 审查通过后释放"，与 04:7/04:30 对齐；补"自检"清单或引用 D-1~D-6。
4. 13:14 改为"仅在结论矛盾时"；定义"显式规则""发布"；给用户当轮明确指令定位；补一正一反例。
5. 13:16 区分业务冲突（问用户、标 `[业务口径]`）与技术/文档冲突（主 Agent 裁决 + ADR），与 01:10 对齐。
6. 13:21 与 06 分级挂钩（明确可简化情形、定时任务不得执行退役）；13:26 改为"失效标注 + 例外清单"，解决与 13:25、AGENTS:73 的冲突。
7. 修 13:28 对 11 的失效引用；13:17"或 ADR"按 06:36 收紧为"重大决策必写 ADR"；13 补齐 push 层与分支条款，接住 08:19 的委托。
