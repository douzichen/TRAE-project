# C 路审计报告：覆盖性与外部适配

> 审计对象：`/workspace` 规则库（AGENTS.md、rules/00~12、docs/AGENT-ADAPTER.md、PITFALLS.md、schedules/daily-retro.md、scripts/、.githooks/）
> 审计方式：只读。未修改任何既有文件，未执行 git 写操作；仅新建本报告。
> 审计时间：2026-11-18

## 0. 结论摘要

- 规则库对"单 Agent 顺序执行"覆盖较好，对"多 Agent 并发 / 需求变更 / 功能下线 / 敏感数据 / 结论冲突 / 审计资产被删"六类真实场景存在结构性缺口，其中 3 项 P0。
- 跨 Agent 适配文档（AGENT-ADAPTER.md）存在 6 处可被豆包/千问/DSH/WorkBuddy 误读的表述，最严重的是"可降级"缺少边界，以及全文未纳入 rules/12 的"未完整读取必须声明"。

## 1. 覆盖性缺口

判定口径：只看"真实发生时会怎样"，不看条款数量。每条给出触发场景、现状证据、缺什么。

### P0-1 多 Agent 并行改同一批文件：无并发控制与冲突裁决

- **触发场景**：主 Agent 同时派发两个子 Agent 改 `rules/` 或 `README.md`；或本地 TRAE 与外部 Agent（豆包/DSH）同时改同一分册。
- **现状**：`rules/04-roles-and-dispatch.md:36` 只要求"只许改哪些文件/目录、不许碰哪些"，是**单任务**边界；`rules/08-alignment-and-versioning.md:19` 只说"每个功能一个分支 + 一次合并"，没有任何并行约定。
- **实证**：`grep -rn "并行" rules/` 仅命中 `rules/08-alignment-and-versioning.md:22`，且指的是 remote/本地镜像，不是并发写入。
- **缺口**：① 无文件/目录认领（claim）或锁；② 无"两个 Agent 不得并行改同一文件"的禁止条款；③ 无冲突处理流程（谁 rebase、冲突片段以谁为准、合并后是否重跑门禁）；④ 无"合并后再审一次"的要求；⑤ 无"同一分支多会话提交"的次序约定。
- **风险**：一方的改动被覆盖而不自知；审查只看了自己那一份 diff；`md_check` 全绿但语义已互相矛盾。

### P0-2 密钥 / 敏感数据：只有一句原则，没有可生效的防线

- **触发场景**：Agent 把真实财税明细贴进 PRD；把 Token/密码写进脚本；把 `.env`、含身份证的样例数据提交；外部 Agent 读取 `.secrets/`。
- **现状**：`rules/08-alignment-and-versioning.md:23` 一条"敏感信息不入库"；`skills/S-001-subagent-dispatch.md:31` 禁读 `.secrets/`；`.gitignore` 覆盖 `.secrets/`、`.env`、`.env.*`。
- **实证**：`scripts/` 下无任何密钥/敏感模式扫描——`grep -iE "secret|password|token|AKIA|PRIVATE KEY" scripts/` 仅命中 `pre-push-check.sh` 的**恢复**逻辑（第 8-12 行），无拦截逻辑。`.githooks/pre-commit:4-8` 依次跑 md_check / link_check / context_budget / delivery_report，全部是结构校验。
- **缺口**：① pre-commit 无 secret/PII 扫描（`deploy-key.pub` 可入库、私钥不许入库，靠自觉）；② 泄露后的处置缺失（吊销、轮换、历史清理、通知）；③ "脱敏"没有判定标准（哪些字段、何种替换）；④ 敏感数据在 `.uploads/`、`reports/`、`docs/` 的存放规则空白（`.uploads/` 被忽略，但报告目录没有）。
- **风险**：红线级违规零拦截；一旦泄露，规则库未给任何止损步骤。

### P0-3 误删审计资产：现有校验无法发现

- **触发场景**：以"清理过期内容"为名删除最新一条 P-00x、删除 ADR、删除审查结论或交接快照。
- **现状**：`rules/06-quality.md:37` 只有文本禁令"审计资产永不算历史包袱，不得以清理为名删除"。
- **实证**：`scripts/md_check.sh:19-27` 仅校验 P 编号"从 P-001 起连续递增"；**删掉末条 P-009 后序列 P-001~P-008 仍连续，校验照常通过**。ADR 只做索引链接存在性（`link_check.sh:10-19`），无数量/哈希基线；审查结论、交接文档根本没有规定存放目录，也无存在性检查。
- **缺口**：① 审计资产清单与基线（文件 + 内容哈希）；② 删除/截断即拦截的检查；③ 审查结论、交接快照的固定落盘位置；④ 变更审计资产的留痕要求。
- **风险**：P-009 自己解决的"可追溯性"被一次清理抹掉，且系统会报"校验通过"。

### P1-4 需求变更后的文档回滚：无流程

- **触发场景**：口径改变（如计税方式调整），旧的 PRD/FSFSD/交接文档/ADR 仍被后续会话当作有效依据。
- **现状**：`rules/11-rollback.md` 全册仅 1 条（第 5 行）"改前准备回滚手段"；`rules/08-alignment-and-versioning.md:21` 只写"改错了用 revert 或切回指定 commit"。
- **缺口**：① 无变更申请/变更单；② 无"口径变更→影响面重跑→哪些文档作废/升版"的清单；③ 无 tag 与文档版本对应规则（08:20 只说"如 `prd-v1.2`"，未规定何时必须打）；④ 无回滚后重跑门禁、通知各 Agent、更新待确认清单的步骤；⑤ 无"回滚到哪一版"的判定依据（以 tag 还是交接文档为准）。
- **风险**：回滚只回代码不回文档，或回了文档但外部 Agent 仍引用旧 tag。

### P1-5 用户说"这个功能不要了"：无下线规则

- **触发场景**：用户取消某功能/某报表/某流程。
- **现状**：`grep -rn "下线\|废弃\|退役" rules/` **零命中**；`rules/06-quality.md:37` 只说审计资产不删。
- **缺口**：① 未区分"业务资产可下线"与"审计资产必须留存"，Agent 可能为"断舍离"删掉相关 ADR/PITFALLS；② 代码、文档、skill、workflow、定时任务、待确认清单各自的处置动作未定义；③ 残留引用（README、INDEX、BACKLINKS、S-001 模板）清理无要求；④ 无下线记录与"为什么不要了"的留档（后续会话可能重新提出来）。
- **风险**：要么删过头（丢审计链），要么留一堆无人认领的引用，后续会话按旧文档继续实现已取消的功能。

### P1-6 Agent 之间说法不一致：无裁决优先级与升级路径

- **触发场景**：两个子 Agent 引用不同章节得出相反结论；外部 Agent 的报告与本仓库规则冲突；主 Agent 与用户业务判断冲突（财税已由 05 覆盖，非财税无覆盖）。
- **现状**：`rules/04-roles-and-dispatch.md:29` 主 Agent 审查；`rules/08-alignment-and-versioning.md:22` 仓库为唯一权威副本；`AGENTS.md:3` 细则优先于摘要。三处都只解决"谁权威"的一个侧面。
- **缺口**：① 无明确优先级链（ADR > rules 分册 > PRD > skill/workflow > 转发内容/口头）；② 无"冲突未裁决前冻结哪一方产出"的规则；③ 无升级到用户的判定条件（哪些冲突必须上报、哪些必须自行裁定）；④ 无冲突记录落点（应进 PITFALLS 还是 ADR）。
- **风险**：各 Agent 各取所需，最终由用户发现矛盾（P-005 已发生过一次环境分叉，属同类根因）。

### P2-7 外部/只读 Agent 的写权限边界

- `docs/AGENT-ADAPTER.md:59` 要求"另开分支、提 PR，由本项目维护者审查合并"，但仓库侧没有分支保护、审批人、合并权限的约定；`rules/08-alignment-and-versioning.md:28` 直接 `git push origin main`。外部 Agent 完全可以照 08 直推 main，与适配文档冲突。
- 无"谁能改 rules/、谁能改 PITFALLS.md"的角色权限矩阵（04 只分主/子，未分内外）。

### P2-8 门禁脚本自身与账本脱节

- `scripts/context_budget.sh:11-21` 使用 `[P-010]` 标签，但 `PITFALLS.md` 全文无 P-010（grep 无匹配），违反 `rules/10-lessons.md:8`"出坑即记账"；该防复发机制没有对应坑条目，后续无法追溯为何设预算。
- 实测最小必读集恰为 **150/150 行**（`AGENTS.md` 88 + `00` 15 + `01` 20 + `02` 27），零余量；再加一行即拦截，规则库已无增长空间，却没有触发 12:35 的"拆分或摘要化"动作。
- `README.md:10-22` 仍只列 `00~11`，缺 `12-context-budget.md`；`README.md:53-57` 缺 `context_budget.sh`、`tool_entrypoints.sh`；`README.md:49` 只列 ADR-001（实际 4 个）。且无脚本校验 README 与 `rules/`、`docs/adr/` 的一致性。

## 3. 坑账本回归（抽查 7 条）

抽查方法：每条按"声称的防复发机制 → 去对应文件/脚本核对是否真实存在、是否真能拦截"。

### 3.1 名不副实

**P-004（状态：已落实·自动检查）**

- 声称：`md_check.sh` 校验四项——S/W 登记 INDEX、P 编号连续、AGENTS.md 章节不重复、**（新增时）入口路径存在**。
- 实测：`scripts/md_check.sh:7-52` 前三项真实（第 8-17、19-27、29-33 行），**第四项"入口路径存在"无任何实现**；脚本中没有遍历 README 或入口文件路径的代码。实测运行输出 `[P-004] md 完整性校验通过`，删除 `context_budget.sh` 也不会报错。
- 判定：**名不副实（4 项中 1 项虚设）**。

**P-006（状态：已落实·章节固化 + 机械防误删）**

- 声称："`md_check.sh` 新增检查 7：AGENTS.md 缺失「用户背景」等关键章节即拦截提交"。
- 实测：`scripts/md_check.sh:46-52` 的检查 7 只做两件事——关键 `rules/*.md` 文件存在、其路径字符串出现在 `AGENTS.md`。**没有 grep「用户背景」等章节标题**；规则拆分后 `AGENTS.md` 全文 88 行已无「用户背景」章节（该内容在 `rules/01-user-profile.md`）。把 `rules/01` 里的职业/技术边界逐条删空，脚本仍通过。
- 判定：**描述与实现不符（只能防整份删文件，不能防章节内容被删）**。

### 3.2 部分不符

**P-007（状态：已落实·章节固化 + 机械防误删）**

- 实测：同 P-006 的检查 7（`md_check.sh:46-52`），只校验 `rules/02-intake-and-dod.md` 文件存在且被总纲登记；删除其中"复述需求/边界确认"条款不会被发现。
- 判定：**部分名不副实**。

**P-002（状态：已升级·全自动草稿生成 + 清单逐项对照）**

- 声称：`delivery_report.sh` 挂 pre-commit，自动生成 D-1（含全文）、D-2、D-3、D-5 草稿。
- 实测：`scripts/delivery_report.sh:13` 的 D-1 只在 changed 含 `AGENTS.md` 时输出全文；改 `rules/*.md` 时走 `:19-20` 分支，输出"AGENTS.md 未改动 → 无全文义务"。而 `rules/02-intake-and-dod.md:15` 明定 D-1 覆盖"AGENTS.md **或任一 rules 分册**"。这是 P-009 扩展 D-1 范围后未回改脚本形成的断点。
- 判定：**部分不符（对改规则的场景反而给出免责话术，与铁律冲突）**。

**P-009（状态：已落实·路由表 + 结构校验 + ADR-003）**

- 声称：路由表、08 五步、孤立分册检查、BACKLINKS 重生成。
- 实测：路由表 `AGENTS.md:6-23`、08 五步 `rules/08:25-31`、孤立分册检查 `scripts/link_check.sh:34-44`、ADR-003 文件均真实。

- 判定：**主体落实，导航仍有一处假入口**（P-009 自述的"接手者不猜着走"未完全成立）。

**P-003（状态：已落实）**

## 4. 建议的最小修复顺序（仅供决策，不在本次执行范围）

1. P0-3 / P0-2：先加"审计资产基线 + 删除拦截"与"pre-commit secret/PII 扫描"，这两项是唯一"违规了也不会响"的红线。
2. P0-1：在 04 或新分册补并发写入的认领、禁止并行同文件、冲突裁决与合并后复检。
3. 修 `delivery_report.sh` 的 D-1 分支与 `md_check.sh` 检查 7 的描述落差（改代码或改措辞，二选一，不能继续两头不一致）。
4. 适配文档补 rules/12 与"未读完声明"，并把"降级"改写为"缺能力 → 替代动作 → 残余风险 → 谁承接"四段式。
5. P1-4 / P1-5 / P1-6 三条流程缺口，建议合并为一册"变更、下线与冲突裁决"（需用户确认，属新增规则，走重级流程）。
