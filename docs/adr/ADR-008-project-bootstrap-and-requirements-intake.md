# ADR-008：项目启动与需求受理采用"规则＋skill＋模板＋workflow"四件套

- 日期：2026-11-18
- 状态：已接受

## 背景

- 本仓库此前只承载规则库（`rules/`、`skills/`、`workflows/`、`docs/`），没有代码基座（当时 `src/` 尚未建立）。下一步要从"只有规则库"进入"真正建项目"，但现有规则缺两条主线：
  1. **有需求文档时**（PRD、需求说明、口径单）：如何从文档走到可运行的骨架，中间不得跳步；
  2. **无需求文档时**：如何先完成需求收集与确认，再建项目，而不是"边写边想"。
- 同时"自己讨论自己写"的老问题再次出现：同一个执行单元既提出问题、又代拟答案、又宣布需求成立，需求被 Agent 自身假设填满，用户真实口径未进入；到验收时无法区分"用户要的"与"Agent 猜的"，也无法回查是哪一步失守。
- 既有约束不可绕：用户为财税从业者，技术决策不得推回用户（[01](../../rules/01-user-profile.md)、红线 2）；需求含财税判断须写明政策条款（[05](../../rules/05-requirement-review.md)）；交付须 D-1~D-7（[02](../../rules/02-intake-and-dod.md)、[15](../../rules/15-delivery-dod.md)；本 ADR 成文时为 D-1~D-6，后增 D-7）；改变规则含义须 ADR（[06](../../rules/06-quality.md)、[ADR-006](ADR-006-rule-change-two-tier.md)）；审查分工不得自我闭环（[04](../../rules/04-roles-and-dispatch.md)、[ADR-005](ADR-005-first-self-audit-ruling.md)）。
- **已定边界**（用户已确认的口径，本项目后续项目默认继承）：
  - 形态：**内网服务 + 网页**；
  - 数据：真实数据可进测试环境，但**必须脱敏**；
  - 外联：**禁止落第三方服务**，含遥测、埋点、外部 API、公有云托管；
  - 技术栈：**Python + PostgreSQL + 轻前端（Jinja/HTMX）优先**。

## 候选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 只写散文规则 | 在规则分册中用一段自然语言说明"先收集需求再建项目" | 成本最低，当天可写完 | 每次执行不一致；没有可判定条款就无法验收；同一句话可被解释成"问一句也算收集"；"自己讨论自己写"没有卡点，老问题照旧复发 |
| B 只做脚本脚手架 | 写 `scripts/new-project.sh`，一条命令生成目录与依赖 | 建仓快；目录统一 | 需求阶段无法脚本化——问什么、谁答、答到什么程度算完，脚本给不出判定；本仓库尚无代码基座，脚手架本身要先选型、定目录契约与门禁，等于用未验证工具生成未验证结构；判断被埋进脚本即黑箱 |
| C 规则＋skill＋模板＋workflow 四件套（**采纳**） | 规则给可判定条款，skill 给可复用步骤，模板固定需求卡片与初始化决策，workflow 画端到端两条分支 | 有验收点、有唯一卡点（用户确认）、可复用、可审查分工；模板把"该问什么"固化，减免漏项 | 四份产物须同步维护（[03](../../rules/03-skill-sync.md) 副本一致性、[08](../../rules/08-alignment-and-versioning.md) 对齐）；单次建设成本高于 A/B |

## 决策

采纳方案 C。四件套职责互不替代，缺一即视为未落地：

| 件 | 职责 | 落地位置 | 状态 |
| --- | --- | --- | --- |
| 规则 | 写"可判定条款"：入口判定、确认完成条件、退回条件 | [rules/14-project-bootstrap.md](../../rules/14-project-bootstrap.md)（R1~R6、A1~A8、内网与数据红线） | 已建立 |
| skill | 写"可复用步骤"：有文档 / 无文档两条分支的前置输入、步骤、验收 | [S-003](../../skills/S-003-requirements-intake.md)（需求侧）、[S-002](../../skills/S-002-project-bootstrap.md)（创建侧） | 已建立 |
| 模板 | 固定"需求卡片"与"新项目初始化决策" | [templates/RQ-CARD.md](../../templates/RQ-CARD.md)、[templates/ADR-000-project-init.md](../../templates/ADR-000-project-init.md) | 已建立 |
| workflow | 画端到端图，串联两条分支与卡点 | [W-001-new-project.md](../../workflows/W-001-new-project.md) | 已建立 |

**入口判定（规则层的判定口径）**：

1. 存在需求文档 → 走"文档受理"分支：抽取口径 → 逐条标注出处 → 缺口列待确认 → 用户确认 → 建仓；
2. 无需求文档 → 走"需求收集"分支：按需求卡片必答项提问 → 用户逐条答复 → 形成需求卡片 → 用户确认 → 建仓；
3. 两者都不满足（只有一句口头想法）→ 一律归入"需求收集"，不得直接建仓。

**"自己讨论自己写"的治法（硬性条款）**：

- 需求卡片固定三栏：**用户已确认 / 待确认 / Agent 假设**；"Agent 假设"栏**不得**进入选型、建仓或验收标准，只能作为待确认项呈现。
- 提问与作答不得由同一执行单元闭环：子 Agent 起草需求卡片 → 主 Agent 核对 → 用户逐条确认；未确认项按 [07](../../rules/07-pending-and-handoff.md) 列入交接。
- 每个必答项必须附**用户原话或需求文档原文位置**；无出处即判为未确认。
- 确认率未达 100% 不得建仓；确需先建骨架探路，骨架代码不得含业务口径，且必须在需求卡片中登记"探路假设"。

## 可验证红线（脱敏、政策、第三方与离线）

以下三条不接受"规则写了即可"，每条都必须给出可执行证据；证据缺失即视为该项目未通过初始化。判定口径写入 [rules/14](../../rules/14-project-bootstrap.md) 的红线与 [templates/ADR-000-project-init.md](../../templates/ADR-000-project-init.md) 的登记项。

### 脱敏

- 字段清单至少覆盖：**姓名、身份证号、手机号、银行账号、纳税人识别号、地址、发票号、凭证摘要**。
- 算法须**不可逆**：禁用"保留后四位＋主键"这类可重识别做法；须记录所用算法、碰撞处理与可关联能力。
- 必须给出一条校验命令（如 `<make pii-check>`），扫描**测试库、日志、备份、导出**四类载体，输出抽样报告（抽样量、命中数、残留字段、命令输出、日期、执行人）并入库存档。
- "有脱敏脚本"不等于通过：无实测报告即判未脱敏。

### 政策可回溯

- 每个新项目维护政策清单，字段固定：**政策名称、文号、生效日、失效日、核实日期、复核周期、复核状态**。
- 复核周期到期即触发复核，结论写回清单并更新核实日期；过期未复核的政策不得作为验收依据。

### 第三方与离线（三项必查）

1. **外链域名静态扫描**：页面与构建产物不得引用 CDN 字体、图表、图标库；留存扫描命令、允许域名白名单与扫描结果。
2. **CI 断网执行**：无离线 runner、未做断网构建的项目，不得声称"可离线/合规"；留存断网构建日志。
3. **lock 文件带哈希**＋许可证扫描器（如 `pip-licenses`）输出入库，作为依赖与许可证审查证据。

## 技术栈理由

- **Python**：财税数据处理生态最完整（pandas/openpyxl/日期与金额计算/对账脚本成熟）；语法对审计者可读，计算过程能逐行复核，满足"账务逻辑可审"；单人＋Agent 协作下文档与人才供给最足，维护成本低。不选 TypeScript 后端（账务与表格处理生态弱）、不选 Java（内网小工具的启动与阅读成本不匹配）。
- **PostgreSQL**：事务（ACID）与库层约束（主键/外键/唯一/CHECK/触发器）保证账务一致性，不依赖应用层自觉；可审计查询（只读账号、视图、PITR 时间点恢复）支撑留痕与追溯。不选 SQLite（并发写、权限与审计能力不足）、不选 MySQL（约束与审计能力较弱）。
- **轻前端（Jinja + HTMX）**：内网工具、用户量有限，服务端渲染足够；依赖少（无 Node 构建链）、HTML 即界面，审计者可读；不引入 npm 依赖树，**减少供应链风险**。
- **否决项（硬红线，需写入每个项目的 ADR-000）**：
  - **公有云托管**：数据驻留与出境不可控，违反"不落第三方服务"；
  - **外部 SaaS**：同一原因，且供应商锁定；
  - **重型前端框架**（React/Vue/Angular 及构建链）：内网工具无收益，只增加依赖面与维护成本；
  - **任何遥测 SDK**：会把使用数据与数据样本外发，无例外。

## 项目分级与裁剪

| 级别 | 判定条件 | 四件套裁剪 | 不可裁剪项 |
| --- | --- | --- | --- |
| 脚本工具型 | 单命令/单文件、无长期数据、无并发、无网页 | 只需需求卡片＋目录契约＋门禁＋Walking Skeleton；不写 workflow，不起服务 | 约束清单、门禁、骨架验收 |
| 单机应用型 | 本机运行、单用户、本地数据库 | 规则＋模板＋简化 workflow（可无流程图，须有步骤表）；数据库用本地 PostgreSQL | 同上；另加备份方案 |
| 内网服务型 | 多人访问、常驻服务、共享数据 | 四件套全量；须有部署单元、权限模型、备份与健康检查 | 同上；另加权限与备份演练 |

裁剪红线：裁剪只减"产物数量"，不减"约束清单 / 门禁 / 骨架验收"三项；**脱敏实测报告、政策清单、外链与离线三项必查在任何级别都不得裁**；凡涉个人财税数据，级别**不得低于单机应用型**。

## 否决项及原因

- **否决 A"只写散文规则"**：无法验收，执行结果依赖执行者自觉，等于把老问题从"需求阶段"挪到"解释阶段"，并未解决。
- **否决 B"只做脚本脚手架"**：需求阶段不可脚本化；且无代码基座时先建脚手架属于"用未验证工具生成未验证结构"，选型与目录契约仍要人来定，脚本顶多省 10 分钟。
- **否决"Agent 自问自答后直接给需求结论"**：把用户口径替换为 Agent 假设，违反 [01](../../rules/01-user-profile.md) 与 [04](../../rules/04-roles-and-dispatch.md) 的审查分工，是"球员兼裁判"在需求阶段的翻版。
- **否决"先写代码、后补需求与 ADR"**：审计链断档，事后无法还原"为什么这样建"，与 ADR 优先原则冲突。
- **否决"以行数/文件数判断需求是否收集充分"**：行数是代理指标，与口径完整性不对应。

## 什么条件下应推翻本决策

1. **内网服务实际并发用户超过约 20 人**（或 P95 响应明显退化）：需引入队列/缓存/连接池调优与独立部署拓扑，轻前端与单进程部署方案须重新评估。
2. **出现必须对接的外部系统**（税局、银行、ERP 等）且无法离线或无本地替代：须新立 ADR 记录例外、数据边界与脱敏责任，"禁止第三方服务"不再作为绝对红线。
3. **前端复杂度超过阈值**（复杂表格编辑、实时协同、核心视图状态机超过 3 个）：Jinja+HTMX 维护成本高于框架，允许引入轻量前端框架，但须保留"可离线构建、无遥测"。
4. **连续 3 个项目出现"待确认项在建仓后才暴露"**：说明需求卡片必答项不完备或用户确认流于形式，须重构模板与卡点，而非继续加流程。
5. **单人维护的内网服务超过 3 个**：维护成本不可持续，允许合并为统一平台并重评技术栈。
6. **Python/PostgreSQL 关键依赖停止维护或许可证变更**：基线失效，须重做选型并更新本 ADR。

## 影响与代价

- **正面**：两条分支各有可判定入口；需求阶段有唯一卡点（用户确认率 100%）；"自己讨论自己写"被结构拦住而非靠自觉；选型不再逐项目重复讨论。
- **代价**：每个新项目多一份 ADR-000 与需求卡片，前期约增加 0.5~1 天；四件套需同步维护，模板改版要回溯已建项目并登记差异。
- **新增取证成本**：每个项目多一次脱敏实测（测试库/日志/备份/导出四类载体）、政策清单维护与到期复核、外链扫描＋断网 CI＋hash lock 三项取证；这些证据缺失即不得交付。
- **二阶影响**：`templates/` 成为正式目录，README 与目录巡检需识别；ADR 从"仓库自身决策"扩展到"项目级决策"，用 `ADR-000` 命名区分，避免与仓库 ADR 混号。
- **三阶影响**：技术栈固定后，引入第二种语言/框架须新立 ADR 并在 ADR-000 登记例外，否则默认否决——防止"顺手加一个库"逐步漂移。
