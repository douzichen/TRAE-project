# ADR-010：涉税结论依据门禁——业务/政策类硬约束＋机械判定

- 日期：2026-11-18
- 状态：已接受

## 背景

- 用户为财税从业者，涉税结论不容出错。既有 [05](../../rules/05-requirement-review.md) 已要求"依据必须写实""写不出条款即不作结论"，但**"是否属涉税/政策类"仍靠 Agent 自觉判断**，且交付环节没有任何拦截点。
- 风险有二：① 该硬拦的政策结论按技术问题处理，凭常识补位；② 把命令用法、配置写法也按政策硬拦，导致正常技术文档被误伤、作业无法推进。
- 约束：判定必须**机械可复现**（不看理解力、可照表复核）；技术类不得被误伤；不得为过闸删规则（ADR-007 前提）。

## 候选方案

| 方案 | 内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 全类型硬约束：所有结论都必须给政策名称＋条款 | 口径最严，无甄别成本 | 技术事实无政策可引，误伤面大，必然诱发绕过 |
| B（推荐） | 仅业务/政策类硬约束＋机械判定（路径 / front-matter / 关键词） | 判定可复现，误伤可控，技术类留住效率 | 关键词有误判可能，需人工兜底与回归观察 |
| C | 纯靠人自觉：由 Agent 自行判断要不要引用条款 | 零实现成本 | 已证不可靠（P-006、P-007） |

## 决策

- 采纳**方案 B**：业务/政策类按三条机械规则判定（`docs/policy/**` 或 `docs/business/**` 路径、front-matter `scope: business`、关键词：税、税率、扣除、申报、发票、政策、公告、财税〔），满足任一即命中。
- 命中后为硬约束：结论必须写"政策名称＋具体条款"，给不出即写"尚未核实到对应条款，不作结论"并说明依据由谁提供；禁止用常识、经验、"通常做法"补位。
- 技术类为软约束：可基于工具文档作答，但须标"依据：<来源>/<时间>"，无来源标"未核实"。
- 拦截点放在交付阶段：[15](../../rules/15-delivery-dod.md) 新增 D-7，逐条列"结论 → 政策名称＋条款 → 核实状态"，有"尚未核实"仍下结论即交付不合格。

## 否决项及原因

- **否决 A（全类型硬约束）**：技术事实（命令用法、配置写法）本就无政策条款可引，硬拦的后果不是更严谨而是**大面积误报**；P-015 已记录门禁过宽首跑误报 9 处，同类判定在真实仓库不可用，且会训练出"绕开门禁"的习惯。
- **否决 C（纯靠自觉）**：P-006 证明 Agent 会忘记用户背景、按通用助手口吻作答，P-007 证明不先复述就开工，两者都说明"自觉"不是稳定机制；无机械判定的要求等于只在事故后复盘。

## 已知漏洞及缓解

- **纯对话答复拦不住**：对话中给结论不经提交，pre-commit 无法覆盖。缓解：拦截点前移到交付环节（D-7），任何含业务/政策结论的交付都要列核实状态。
- **外部 Agent 自称"已核实"不可信**：其他 Agent 接入本库时可能自报核实。缓解：要求贴来源（政策名称＋具体条款），无来源即视为"尚未核实"，不得采信自述。
- **关键词误判**：含"税"字的技术文档被误判为政策类。缓解：复核者可注明"判定为技术类"及理由并留档；不得以误判为由调低整体要求，调整须回到本 ADR。

## 什么条件下应推翻本决策

1. **关键词误判导致正常技术文档被拦超过 3 次**：回到本 ADR 调整判定方式（改关键词表、改路径名单或改判据优先级），**不得直接调低要求**。
2. **判定可脚本化**：front-matter 与路径规则可在 pre-commit 稳定解析时，把 D-7 的人工核验升级为机械门禁，软约束范围可再评估。
3. **出现"已核实"造假**：即来源条款与结论不对应，须增加来源可访问性/条款原文校验，而非取消核实要求。
