# ADR-005：规则库首次自检的审查裁定与修复分工

- 日期：2026-11-18
- 状态：已接受
- 性质：**主审裁定记录**（不是生产文档；用于留痕"谁决定、为何这样改"）

## 背景

用户指出流程存在"球员兼裁判"问题：同一个 Agent 既制定规则、又撰写规则、又宣布完成。据此按 rules/04 分工，改为"主审主导 + 子 Agent 生产 + 主审审查"。首次检验采用三路独立审计（结构一致性 / 零上下文可执行性 / 覆盖性与外部适配），全部只读，报告写入 `reports/`。

## 审计结果

三路共报 P0 11 条、P1 约 20 条。主审裁定：**全部成立，无一条驳回**。其中 4 条由主审本人造成：

| 编号 | P0 问题 | 裁定 |
| --- | --- | --- |
| A-1 | 红线 1「动手前读完规则库」与 12 册「禁止整库加载」互相冲突 | 认，改红线 1 措辞 |
| A-3 | 每日复盘任务只读 AGENTS.md 与 PITFALLS，跳过固定必读的 00/01/02 | 认，改任务内容并同步调度器 |
| A-4 | `delivery_report.sh` 的 D-1 只覆盖 AGENTS.md，改 rules 分册时误报"无全文义务" | 认，脚本改为覆盖 AGENTS.md 与 rules/*.md |
| C-3 | 审计资产（坑条目、ADR）被删也能过检 | 认，md_check 增"只增不减"检查 |

## 决策

1. **分工边界**：文档内容（规则、README、适配说明、账本条目）一律**派单**给子 Agent；脚本类机械修复（门禁脚本、生成器）由主审执行并逐条点名。ADR 与审查结论属主审的裁决产物，由主审撰写。
2. **修复方式**：合并为一张固定工单（F1~F11）派给单个执行 Agent 顺序完成，**不允许并行改同一批文件**——并行写同一批文件正是审计发现的 P0 缺口，故同期新增 rules/13 认领机制。
3. **预算**：最小必读集从 150 行压缩到 148 行，留 2 行余量；总纲加设 100 行硬校验（此前只写在文档里、脚本未实现）。
4. **新增机械防线**：`secrets_scan.sh`（敏感信息）、`md_check` 内容级关键词校验与审计资产只增不减校验、`context_budget` 总纲上限校验。

## 否决项

- **否决"由主审直接改文档以加快速度"**：这正是用户指出的问题根源，短期提速换来的是标准失守。
- **否决"提高必读集上限到 170 行"**：等于用改阈值掩盖膨胀，用户明确要的是防止读不完。

## 什么条件下应推翻本决策

1. 子 Agent 连续两轮无法产出通过审查的成果，说明派单粒度或工单质量有问题——此时应先改工单，而不是退回自己写；
2. 机械脚本占比过高导致主审实质承担了生产——此时应把脚本也纳入派单，仅保留审查权。
