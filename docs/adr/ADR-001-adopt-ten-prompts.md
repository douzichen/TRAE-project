# ADR-001：采纳"十条提问法"并做分级触发改造

- **日期**：2026-11-18
- **状态**：已接受

## 背景

用户提供《我用 Agent 干活最爱说的几句 Prompt》十条提问法，要求从程序开发专业角度判断如何在项目中规范落地。原始十条是个人提问技巧，不是可验收的规范；若原文照抄进规则库，会造成规则膨胀、与既有铁律重复、且多条条款无法判定是否执行。

## 候选方案

| 方案 | 内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 十条原话整体照录进 AGENTS.md | 忠实、零解释成本 | 与既有铁律重复 3 条；无法验收；规则库膨胀；小任务被迫全跑 |
| B | 全部改造成脚本自动检查 | 最机械 | 只有 4 条可脚本化，思考类条款无法脚本化，会造出空跑检查 |
| C（采纳） | 分层处置：合并重复项 / 改造为可检产物 / 有条件启用 / 明确不采纳，并加"任务分级触发" | 每条都有落点与产物；避免过度分析；诚实标注不适用项 | 需要解释成本，用户需理解分级 |

## 决策

采纳 **方案 C**，具体处置：

1. 合并：第 1 条并入「问题解决的核心方法」；第 10 条并入既有「坑账本 + 复发即升级」，补每日定时复盘。
2. 改造：第 2 条加"必须给出推荐项"；第 4 条改为必填"影响面表"；第 6 条改为独立子 Agent 扮演反方；第 7 条改为 ADR 优先于 Git 考古；第 8 条改为零上下文接手测试。
3. 有条件：第 5 条仅在项目内无先例时启用。
4. 不采纳：第 9 条（本项目无 PR 流程），待引入 PR 后启用。
5. 结构性补充：任务分级触发（轻/中/重），防止小改动被十条全量拖死。

## 否决项及原因

- **否决方案 A**：会把规则库变成 prompt 仓库，且与既有铁律产生双份表述，违反"文档与文档对齐"红线。
- **否决方案 B**：思考类条款无法脚本化，强行脚本化会产出空跑检查（等价于第 9 条不采纳的理由）。

## 什么条件下应推翻本决策

- 项目引入 PR / 多人协作 / CI 后：第 9 条应启用，分级触发需按真实交付链路重新校准。
- 规则库经"零上下文接手测试"证明已过难用：应合并精简，而不是继续叠加条款。
