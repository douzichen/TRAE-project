# ADR-032：客户数据入库判定——按去向分档，底稿默认不入 git

- 日期：2026-11-25
- 状态：已接受（主会话依用户 2026-11-25 授权裁决）
- 关联：[rules/08](../../rules/08-alignment-and-versioning.md)（落点）、[rules/04](../../rules/04-roles-and-dispatch.md)（外部 Agent 只读边界）、[rules/14](../../rules/14-project-bootstrap.md)（项目侧规则落位）、[rules/10](../../rules/10-lessons.md)（坑的升级）、[P-046](../../PITFALLS.md)、[ADR-026](ADR-026-nine-item-rulings-deadline-desensitization.md)（脱敏判定标准）

## 背景

真实事件：用户项目仓在提交前暂存了 70 个文件，其中 39 个含客户企业实名、12 个含 18 位统一社会信用代码，并含发票号码。提交前扫描发现，随即停止提交。

既有 rules/08「脱敏判定标准」节（ADR-026）只回答"怎么算脱敏"：必删六类、固定占位符、判定三问。它没有回答另一个同样关键的问题——**这类数据能不能入库、能入哪种库**。执行中出现的偏差是：只跑了 `secrets_scan.sh`，把"密钥零命中"当成"可以提交"，忽略实名、税号、发票号码并不在任何密钥模式内。结果是把"脱敏与否"与"去向是否允许"两个判断混成一个。

另有一个方向性错误值得固定下来：对发票明细、申报底稿这类**底稿**做脱敏后再入库，等于让底稿失去与原始凭证、发票逐笔核对的能力，审计价值被毁掉。底稿的正确处置是"不传"，而不是"脱敏后传"。

## 候选方案

| 方案 | 内容 | 结论 | 理由 |
| --- | --- | --- | --- |
| A（采纳） | rules/08 新增「客户数据入库判定」节：先判去向、再判内容，按四档去向给结论 + ADR-032 + P-046 + md_check 关键词门禁 | 采纳 | 与既有「脱敏判定标准」互补且不重复（上节管"怎么脱敏"、本节管"去哪"）；落点符合总纲路由表（文档一致性、提交推送归 08）；rules/08 改动后仍 <120 行 |
| B（否决） | 一律脱敏后提交，不区分去向 | 否决 | 底稿脱敏后无法与原始凭证、发票核对，毁掉可核对性与审计价值；且逐笔脱敏易错、易漏，一旦漏一处即等于未脱敏 |
| C（否决） | 私有仓一律允许入库 | 否决 | "私有"不等于"可外泄"：一旦存在远端（含 fork、镜像、协作者克隆），即构成对外提供面；客户涉税信息进入远端仓的法律与合规风险不因仓库私有而消失 |
| D（否决） | 只改文本说明，不立 ADR、不落坑账本 | 否决 | 新增规则条款属重级（改变含义），按 rules/06 与 ADR-006 须 ADR + 全量交付；仅记账不落条款等于把复发留给记忆 |

## 决策

落点为 rules/08「客户数据入库判定」节，六条判定＋一项落地：

1. **先判去向，再判内容**（顺序不可颠倒）：规则库/公开仓库/共享盘/外部 Agent → 禁止入库，须按上节脱敏为固定占位符或只留路径引用；有远端的私有仓 → 默认不入，仅当"客户委托或内部制度允许 ＋ 成员仅授权人 ＋ 已最小化"三条同时成立才可入，且授权须为可追溯的书面依据（委托合同条款／内部制度编号／邮件，口头不算），提交信息注明数据范围；无远端的本地仓 → 可入，须 `git remote -v` 为空并标注"内部底稿，禁止外传、不推送"，但 `git remote -v` 为空只是必要条件，还须确认该仓不在同步盘、自动备份、镜像路径下，日后添加远端须按"有远端私有仓"重新判定；仅本机文件系统（不入 git）→ 允许，底稿类默认走这一档。
2. **未列即禁（判定兜底）**：未在例示中列出的快照型资料，一律按底稿处理。
3. **底稿默认不入 git**：发票明细、申报底稿（含申报表正本与税局导出 CSV）、银行流水、工资表、试算表等快照型资料，默认用 `.gitignore` 按目录排除；确需版本管理时只允许"无远端本地仓"一档。
4. **不为提交而脱敏底稿**：底稿脱敏后无法与原始凭证、发票核对，等于毁掉审计价值；脱敏只用于必须外传的摘录或报告。
5. **提交前必查（含未跟踪文件）**：先 `git diff --cached --name-only` 与 `git ls-files --others --exclude-standard` 列出全部待入库与未跟踪文件，逐份核对企业/个人名称、18 位统一社会信用代码、发票号码、账号；可用 `git diff --cached -U0 | grep -nE '[0-9]{20}|[1-9][0-9A-Z]{17}'` 初筛，误报高，命中须人工判定；`secrets_scan.sh` 只覆盖密钥，不能替代本项。
6. **判定留痕**：一次判定对应一次提交或一次交付，结论（去向档位＋依据）写进提交信息或交接记录，不靠记忆。
7. **门禁与对账**：`scripts/md_check.sh` 7b 增 4 条 rules/08 关键词门禁（防整节被删，仅存在性、不校验语义）；坑账本新增 P-046；CONFLICT-MATRIX 补 04×08 与 14×08 依据，格子不变。

## 已核对的既有决策

已核对 ADR-015（验证型只读）、ADR-017（写入口唯一）、ADR-026（脱敏判定标准）、ADR-030（外部治理草案不入库）：本节不改变外部 Agent 只读边界，不改脱敏判定标准本身，也不放宽任何既有入口；只在其上补"去向"这一前置维度。外部 Agent 的只读边界仍由 rules/04 单独规定，本节只判数据去向，不另立重复来源。已核对 rules/08 L20-25 版本管理条，L25「仓库为唯一权威副本／本地不留未入库最终版」已加范围限定（客户底稿类资料按下节处置），与"无远端本地仓可入"不冲突。本节与 rules/08 既有「敏感信息不入库」条是同一红线的细化，不构成松绑。

## 对抗审查与零上下文测试（2026-11-25）

独立反方（非修改者）提出 7 条，逐条处置：

1. L25「仓库为唯一权威副本／本地不留未入库最终版」与"无远端本地仓可入"冲突 → 已给 L25 加范围限定，L26 改为"原件不得进入有远端或对外的仓"，无远端档只针对底稿且为默认例外。
2. 「逐文件扫描」无工具支撑 → 改为三条具体命令（`--name-only` / `--others` / `grep` 初筛）＋人工判定；不新增脚本、不推翻 ADR-026 的低误报取舍。
3. 底稿边界与授权不可判定 → 增「未列即禁」兜底、书面授权要求、无远端≠不外流（同步盘/备份/日后加远端）。
4. 未跟踪文件与 `git diff --cached` 矛盾 → 合并为一条，同时列出 untracked。
5. 关键词门禁假绿 → md_check 增 4 个锚点；P-046 明示"只查存在性、不查语义"。
6. 与 04 重复、14×08 依据不实 → 08 只引用 04 边界，14×08 依据改写为"数据红线同向、底稿以 08 为准"。
7. 缺对抗审查与零上下文记录 → 本节即记录。

零上下文测试：新 Agent 仅读 AGENTS.md 与 README，经 AGENTS.md 路由（提交推送/文档一致性→08）与 rules/14「内网与数据红线」指针定位到 08 新节，正确答出四档去向、底稿默认不入 git、无远端本地仓档需 `git remote -v` 为空；结论：通过，认知路径成立。

## 否决项及原因

- B/C/D 如上表。
- 「只在 PITFALLS 记一条、不改规则」：坑账本的防复发优先级是自动检查 > 模板 > 规则文本，仅记账不落条款等于把复发留给记忆（与 ADR-031 同一裁定）。

## 什么条件下应推翻本决策

1. 客户普遍接受可模板化的授权文本（可批量取得"允许进入指定私有仓"的书面同意），使"有远端私有仓"三条同时成立的判定可规模化 → 该档可改为默认允许并简化取证，另立 ADR。
2. 出现可核验的加密仓方案（如仓内字段级加密 + 密钥分离托管，且密钥不入同一远端），能同时满足"可版本管理"与"不构成对外提供" → 底稿档可由"本地仓"上移至"加密私有仓"，另立 ADR。
3. 监管或行业口径变化（对客户涉税信息的存储位置、跨境、可提供范围有新规定） → 四档判定按新口径重排，另立 ADR 取代本节。
4. 若规则库或项目仓出现"无远端本地仓"被长期当成事实上的共享盘使用 → "无远端"一档的取证（`git remote -v` 为空）需升级为定期机械检查，另立 ADR。
