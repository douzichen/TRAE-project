# ADR-003：规则库由单文件改为"总纲 + 分册 + 双向链接"

- **日期**：2026-11-18
- **状态**：已接受
- **触发**：用户提出"是否可以用双向链接的方式，不要存放过多内容，在主文件里写内容并与分支文件创建双向链接"（规则库已增至约 240 行，单文件阅读成本过高）。

## 背景

AGENTS.md 单文件承载全部铁律，随规则增加已到 240 行。问题不是行数本身，而是：每次会话必须整篇读、定位某条规则靠滚动、修改时容易顺手破坏无关条款。

## 候选方案

| 方案 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| A 保持单文件 | 继续追加 | 零 | 越写越难读，最终被跳过或选择性执行 |
| B 总纲 + 分册 + 相对链接 + 自动反向链接（**采纳**） | AGENTS.md 只放红线速查、路由表、索引；细则进 `rules/` 12 册；链接用 Markdown 相对路径，`link_check.sh` 生成反向索引并查死链 | 一次性拆分 + 维护链接 | 摘要与细则可能不一致；链接断了规则就找不到 |
| C `[[wikilink]]` 双向链接 | 用 Obsidian 语法 | 低 | **GitHub 不渲染、其他 Agent 解析不可靠**，等于把可用性押在特定工具上 |

## 决策

采纳 B，并补三条约束控制其风险：

1. **单一事实源**：细则只在 `rules/`；总纲摘要与细则冲突时以细则为准，且须立即修正摘要。
2. **机械校验**：`scripts/link_check.sh` 查死链、查"归属总纲/相关分册"结构、查分册是否在总纲登记、查孤立分册（无任何其他分册引用），并在 pre-commit 阻断。
3. **体积红线**：单分册 > 120 行考虑再拆；总纲 > 100 行须精简，防止总纲重新膨胀。

## 否决项及原因

- 否决 C：`[[wikilink]]` 在 GitHub 与多数平台不渲染，外部 Agent 无法可靠解析，违反"其他 Agent 拿到就能读懂"的核心要求。
- 否决"按主题自由拆分"：无路由表时，"这条新规则该写哪册"要靠猜；已补路由表（AGENTS.md「新规则落到哪一册」）。
- 否决"总纲也保留全部细则副本"：双份正文必然漂移，违反对齐红线。

## 什么条件下应推翻本决策

- 若实际使用中"某个分册从未被读过"（零上下文测试反复暴露某册无人访问），说明拆得过细，应合并该册而非继续增加分册。
- 若总纲被反复绕过直接读细则导致摘要失真，应收紧为"总纲只允许放红线与路由，禁止放任何可执行细则摘要"。
