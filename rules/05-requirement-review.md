# 需求定义审查

> 归属总纲：[AGENTS.md](../AGENTS.md)｜分册编号：05｜本文件为唯一细则来源

- **开发技术类问题**：用户不懂开发技术，Agent 必须自己判断并承担技术方案；不得把技术选型、实现细节当作需要用户拍板的事。
- **财税业务类问题（用户原话照录，2026-11-18 修订版）**："不要默认我提出的财税业务方面的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标，更不要错误的、不符合税法政策规定的需求认为是对的，如果存在更值得解决的问题，或有错误的需求（不符合税法政策规定的）必须直接指出来。"
- 指出问题必须**附替代方案或合规做法**，只否定不给路等于没做。
- **依据必须写实（强度不下调，用户明确要求 2026-11-18）**：涉及税法判断时，**必须写出政策名称与具体条款**，并**核实清楚**——财税是专业且不容出错的领域。禁止凭记忆编造条款号、禁止用已失效规定下结论。
- **核实不到时的处理**：确因资料缺失或无法确认时，必须明确写"**尚未核实到对应条款，不作结论**"，并说明需用户提供或需补充核对的渠道；**不得用"需核实"当降级借口照常给结论**，也不得用模糊表述掩盖未核实状态。
- **业务/政策类判定方式（机械，不靠自觉）**：满足任一即为业务/政策类——① 文件位于 `docs/policy/**` 或 `docs/business/**`；② front-matter 含 `scope: business`；③ 文本含关键词：税、税率、扣除、申报、发票、政策、公告、财税〔。
- **硬约束**：业务/政策类结论必须写出"政策名称 + 具体条款"；给不出即写"**尚未核实到对应条款，不作结论**"并说明需谁提供依据；**禁止**用常识、经验、"通常做法"补位。
- **技术类（软约束）**：技术事实（命令用法、配置写法）可基于工具文档作答，但须标"依据：<来源>/<时间>"；无来源标"未核实"。
- **裁量权与优先级**：财税业务的最终裁量权在用户（见「用户背景」）；但**"合规"结论不由用户裁量**——Agent 的责任是据实指出风险并留档，**不替用户裁定，也不为用户的做法背书**：不得在文档中把不合规做法写成"合规"。用户坚持时，记录"已告知风险、用户决定"，再按用户决定执行。
