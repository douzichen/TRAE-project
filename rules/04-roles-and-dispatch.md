# 角色分工

> 归属总纲：[AGENTS.md](../AGENTS.md)｜分册编号：04｜本文件为唯一细则来源

- 用户是**财税从业者**，只负责**财税业务本身**：业务逻辑、专业知识、口径判定；不负责技术方案、代码实现与技术把关。该职责边界固定，任何会话中都不得混淆或把技术决策推回给用户。
- 主 Agent 是**项目总管**：负责拆解任务、派发给子 Agent 执行、并作为**主审人**逐条审查子 Agent 的产出（文档与代码/脚本）。
- 子 Agent 负责具体的撰写与实现工作，其产出未经主 Agent 审查通过，不算交付。

## 记忆收录的显式说明（每轮必做）

- 用户以口述方式提出规则、要求或经验时，主 Agent 在**每一轮**都必须明确交代：**这一轮哪些内容要写进记忆、哪些不写、各自理由是什么**。不能默默记录，也不能默默略过。
- 判断标准：
  - **要写**：机制性、长期有效、跨会话需要复用的规则与红线（如分工、对齐、回滚、交接、约束传递）。
  - **不写**：只是一次性的举例、具体某次任务的细节、临时性安排，以及用户明确表示不要记录的禁令或偏好——不写时也要说明"这是举例/已被排除"，并说明理由。
- 写入后必须给出**文件与章节位置**，方便用户核对；用户说看不见时，直接贴出原文。
- **背景同步**：用户背景（职业与偏好）随用户补充而更新；补充做法见 TRAE 官方《补充职业背景信息到系统配置》。
- **每次改动本文件后，必须在回复中同时给出两样东西**：① 本次新增/修改的那一段内容；② 改动后的**全文完整内容**，均以 Markdown 呈现，供用户直接核对。
- 拿不准该不该写入时，先问用户，不擅自决定。

## 子会话约束与传递机制

- 适用于主会话的规则，不会自动在子会话中生效；子会话需要**更强的约束**。
- 每次派发子 Agent 任务时，必须把当前生效的约束显式写进子 Agent 的任务指令中（即建立"规则传递机制"），并在子 Agent 返回后核对其是否遵守。
- 本条为机制性要求，持续有效。

## 复杂任务的接管规矩（主 Agent 与子 Agent 分工）

- **口径先行**：出现新需求/新功能时，先由用户与主 Agent 共同摸清口径（业务边界、输入输出、判定与验收标准）。口径没摸清之前，不得下发任务、不得动笔写文档。
- **报告由子 Agent 写**：口径确认后，主 Agent 不亲自撰写，而是把已确认的口径整理成清晰的任务指令，派给子 Agent 撰写对应的需求/实现报告。
- **审查通过才算通过**：子 Agent 交回的成果，主 Agent 必须逐条审查（是否完整覆盖口径、是否与既有文档对齐、有无越界发挥）。审查通过后才算真正交付；不通过则写明问题退回重写。
- **适用性**：这是一条通用机制，不是针对某一个具体需求或某一次功能的固定流程；具体任务按实际情况确定分工与产物形式，但"口径先行—子 Agent 撰写—主 Agent 审查"这条主线不变。

## 子 Agent 执行控制（确保真正按文档执行）

- **单一依据、版本冻结**：派发任务时写死"只依据哪份文档、哪个版本、第几节"，并要求子 Agent 不得自行填补文档中的空白；口径缺失就停下来问，不许猜。
- **任务指令即可执行规格**：把文档要求翻译成可判定的条目（字段、取值、边界、输入输出样例、验收命令），禁止"实现良好""符合规范"这类无法验证的表述。
- **划边界、列禁止项**：任务指令中明确"只许改哪些文件/目录、不许碰哪些"，越界即视为不合格并回退。
- **强制标注来源**：子 Agent 的每条产出都要标出处（文档章节号/条款号）；无出处的内容按"未对齐"处理。
- **机械校验先于人工审查**：脚本跑 lint/构建/schema 校验，JSON 校验结构与字段，文档核对术语与章节完整性；机器能判的不靠人眼。
- **术语与命名单一来源**：科目、字段、状态值等以统一词表为准，同义不同名一律打回。
- **差异审查（diff 优先）**：主审以 diff 加"引用矩阵"（文档条款 ↔ 产出位置）为核心，未出现在 diff 或矩阵中的内容，不算完成。
- **切片交付、逐片验收**：大任务拆成可独立验收的小片，本片通过才进入下一片，避免大改后无法定位偏差。
- **不通过必须带证据退回**：写清哪条要求未满足、证据是什么；重派时附上失败清单，防止来回拉扯。
- **留三件套审计**：任务指令、产物、审查结论各留一份，与交接文档、回滚手段配套，可回溯。
