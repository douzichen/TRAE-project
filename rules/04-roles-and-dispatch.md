# 角色分工

> 归属总纲：[AGENTS.md](../AGENTS.md)｜分册编号：04｜本文件为唯一细则来源

- 用户是**财税从业者**，只负责**财税业务本身**：业务逻辑、专业知识、口径判定；不负责技术方案、代码实现与技术把关。该职责边界固定，任何会话中都不得混淆或把技术决策推回给用户。
- 主 Agent 是**项目总管**：负责拆解任务、派发给子 Agent 执行、并作为**主审人**逐条审查子 Agent 的产出（文档与代码/脚本）。
- 子 Agent 负责具体的撰写与实现工作，其产出未经主 Agent 审查通过，不算交付。

## 记忆收录的显式说明（每轮必做）

- 用户以口述方式提出规则、要求或经验时，主 Agent 在**每一轮**都必须明确交代：**这一轮哪些内容要写进记忆、哪些不写、各自理由是什么**。不能默默记录，也不能默默略过。
- 判断标准：
  - **要写**：机制性、长期有效、跨会话需要复用的规则与红线（如分工、对齐、回滚、交接、约束传递）。
  - **不写**：只是一次性的举例、具体某次任务的细节、临时性安排，以及用户明确表示不要记录的禁令或偏好——不写时也要说明"这是举例/已被排除"，并说明理由。
- 写入后必须给出**文件与章节位置**，方便用户核对；用户说看不见时，直接贴出原文。
- **背景同步**：用户背景（职业与偏好）随用户补充而更新；补充做法见 TRAE 官方《补充职业背景信息到系统配置》。
- **每次改动本文件后，交付义务必须履行**：按 [rules/15-delivery-dod.md](15-delivery-dod.md) 的 D-1 分级执行——重级给全文，轻级只给修改段（改动段落原文＋改动位置），均以 Markdown 呈现，供用户直接核对。
- 拿不准该不该写入时，先问用户，不擅自决定。
- **用户指令观察（[ADR-023](../docs/adr/ADR-023-rulebase-evolution-mechanisms.md)，2026-11-21 起，试用期至 2026-12-21）**：在上述交代中同步记录"用户指令观察"——只记**显式偏好语句**（日期＋场景＋原话或脱敏转述），不做无差别全录；原话同步落 `.local/` 原始层（不入库不推送，可识别要素必剔，见 [rules/08](08-alignment-and-versioning.md)）；同类重复 ≥2 才触发提炼，当轮以 `[偏好]` 向用户确认后按重级流程入 [rules/01](01-user-profile.md)「指令偏好」；拒绝即归档不追问。机械保障暂缺，漏记按 [rules/10](10-lessons.md) 复发即升级。

## 子会话约束与传递机制

- 适用于主会话的规则，不会自动在子会话中生效；子会话需要**更强的约束**。
- 每次派发子 Agent 任务时，必须把当前生效的约束显式写进子 Agent 的任务指令中（即建立"规则传递机制"），并在子 Agent 返回后核对其是否遵守。
- 派发子 Agent 时，首条消息必须显式写明"先读哪些文件"，**不得假设对方已知规则**（依据 [P-016](../PITFALLS.md)）。
- 判断子 Agent 是否遵守，只看交付产物（D-1~D-7、影响面表、依据核验、引用矩阵）；**"我已读过规则"不作为证据**。
- 本条为机制性要求，持续有效。

## 复杂任务的接管规矩（主 Agent 与子 Agent 分工）

- **口径先行**：出现新需求/新功能时，先由用户与主 Agent 共同摸清口径（业务边界、输入输出、判定与验收标准）。口径没摸清之前，不得下发任务、不得动笔写文档。
- **报告由子 Agent 写**：口径确认后，主 Agent 不亲自撰写，而是把已确认的口径整理成清晰的任务指令，派给子 Agent 撰写对应的需求/实现报告。
- **审查通过才算通过**：子 Agent 交回的成果，主 Agent 必须逐条审查（是否完整覆盖口径、是否与既有文档对齐、有无越界发挥）。审查通过后才算真正交付；不通过则写明问题退回重写。
- **适用性**：这是一条通用机制，不是针对某一个具体需求或某一次功能的固定流程；具体任务按实际情况确定分工与产物形式，但"口径先行—子 Agent 撰写—主 Agent 审查"这条主线不变。

## 子 Agent 执行控制（确保真正按文档执行）

- **单一依据、版本冻结**：派发任务时写死"只依据哪份文档、哪个版本、第几节"，并要求子 Agent 不得自行填补文档中的空白；口径缺失就停下来问，不许猜。
- **任务指令即可执行规格**：把文档要求翻译成可判定的条目（字段、取值、边界、输入输出样例、验收命令），禁止"实现良好""符合规范"这类无法验证的表述。
- **划边界、列禁止项**：任务指令中明确"只许改哪些文件/目录、不许碰哪些"，越界即视为不合格并回退。
- **强制标注来源**：子 Agent 的每条产出都要标出处（文档章节号/条款号）；无出处的内容按"未对齐"处理。
- **机械校验先于人工审查**：脚本跑 lint/构建/schema 校验，JSON 校验结构与字段，文档核对术语与章节完整性；机器能判的不靠人眼。
- **术语与命名单一来源**：科目、字段、状态值等以统一词表为准，同义不同名一律打回。
- **差异审查（diff 优先）**：主审以 diff 加"引用矩阵"（文档条款 ↔ 产出位置）为核心，未出现在 diff 或矩阵中的内容，不算完成。
- **切片交付、逐片验收**：大任务拆成可独立验收的小片，本片通过才进入下一片，避免大改后无法定位偏差。
- **不通过必须带证据退回**：写清哪条要求未满足、证据是什么；重派时附上失败清单，防止来回拉扯。
- **留三件套审计**：任务指令、产物、审查结论各留一份，与交接文档、回滚手段配套，可回溯。

## 验证型 Agent 只读（2026-11-18，用户明确限制，见 [ADR-015](../docs/adr/ADR-015-validation-agents-readonly.md)）

- **定位**：豆包、豆包工作、千问助手、DSH、WorkBuddy 等外部 Agent 接入本规则库，是为了**实测规则能否被正确执行**，不是参与维护。
- **允许**：clone / pull / 读取 / 在自己副本试跑脚本与门禁 / 为跑门禁做**本地** commit（`md_check` 会拦未提交散改）。
- **禁止**：`git push`、开 PR、改远端任何分支或标签、把任何文档上传到 GitHub；不得安装 `.githooks`（`pre-push-check.sh` 会自动恢复推送凭据），不得配置 deploy key / token / `gh auth login`。
- **接入方式**：HTTPS 匿名 clone，`GIT_TERMINAL_PROMPT=0`。公开仓库无法阻止任意第三方 fork 或开 PR，本条约束的是自愿配合验证的 Agent。
- **交付要求**：D-5 须写"未推送"，并附任务前后 `git ls-remote origin` 的 HEAD/分支快照；主 Agent 以此核验，不只听自述。
- **写入权**：仅主 Agent。外部 Agent 确需写入时，须用户单独授权并记 ADR，否则视为违规。
- **不参与并行**：外部 Agent 不认领 `docs/CLAIMS.md`，不触发并发协议（[13](13-concurrency-and-lifecycle.md)）；其副本分叉不影响主线。

## 跨项目运行模型：规则唯一通道与写入口（2026-11-19，用户定调，见 [ADR-017](../docs/adr/ADR-017-cross-project-operating-model.md)）

- **规则唯一通道**：每个新项目开工只从本仓库拉取规则文档（落位三步见 [AGENTS-GLOBAL.md](../AGENTS-GLOBAL.md)「新项目引导」）；本仓库永不承载新项目及其代码（[rules/01](01-user-profile.md) 仓库定位边界）。**落位＝把规则复制到项目目录，不是把项目放回本仓库**。
- **写入口唯一**：规则文档的新增与修改只经主会话（本地 TRAE）、按用户批准流程进行；外部验证 Agent、任何子会话、定时任务会话均不得修改或上传规则文档。
- **新项目仓库自建自管**：新项目远端由开发方（执行 Agent 体系）自行创建与维护，与本仓库**完全隔离**；执行 Agent 对其项目仓拥有完全管理权，**项目自身的代码与文档均可推送**（须按本规则库流程产出、经其主/子体系终审的正确内容）。上传红线**仅指向规则库**：任何项目内容不得推入本仓库。
- **拉取式迭代**：开工拉取最新规则并记录 commit。**开工强制握手（[ADR-019](../docs/adr/ADR-019-startup-sync-gate.md)）**：开工自检发现本地落后远端（落后 N>0）时，须先 `git pull --ff-only origin main` 并报新 commit，否则不得开工；用户显式指令"锁定版本/暂不更新"时，交付声明"落后 N、按用户指令锁定"即合规豁免（依据 [rules/13](13-concurrency-and-lifecycle.md) 裁决第 1 位用户当轮指令）。规则库更新后用户可另行下发"重新拉取"指令（中途同步），执行 Agent 首条回复报 `git rev-parse --short HEAD`，主会话/用户以 `git ls-remote origin main` 核验；未报 commit 的"按新规则执行"视为未验证。**重拉机制（[ADR-018](../docs/adr/ADR-018-clean-copy-repull.md)）**：以项目内**只读干净副本**为基（副本永不改写），在副本内 `git pull --ff-only` 并生成新旧差异清单；`rules/`、`scripts/`、`.githooks/`、`templates/` 直接同步新版；项目根的混合体文件（AGENTS.md 等"通用层＋项目特定层"）**禁止整文件覆盖**，须逐段合并、保留项目特定段；**任务片边界才换规**，不在任务片中途切换验收基准。本条适用于执行 Agent 在其自建项目内的重拉；验证型 Agent（只读）不适用本条。**片边界＝当前片审查通过（认领状态改「已完成」）或已放弃、下一片开工前**（[13](13-concurrency-and-lifecycle.md)）；重拉后于项目实例复跑 `sh scripts/md_check.sh`，通过方可进下一片。
- **产出终审归属**：新项目内的 PRD、ADR、代码由执行 Agent 自身的主/子体系按本规则库流程终审，不经主会话复检；发现规则缺口走上一条"拉取式迭代"回到主会话。
