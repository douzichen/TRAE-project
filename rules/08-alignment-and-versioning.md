# 对齐要求

> 归属总纲：[AGENTS.md](../AGENTS.md)｜分册编号：08｜本文件为唯一细则来源

- **文档与文档对齐**：各文档之间必须口径一致，尤其是 PRD、FSFSD 等需求与设计文档，不允许各自表述、互相矛盾。
- **文档与实现对齐**：脚本、JSON 等实现产物，必须严格按 PRD、FSFSD 等文档的要求编写与执行，不得自行发挥、不得超出文档范围。
- 上述两条是底线、是红线，不是一次性检查，而是每轮交付都要做的持续动作；发现不一致时，先纠正再交付。

## 文档一致性维护（对账要求）

- 版本变化后必须逐条核对下列文档的实际状态：**PRD 更新日志、Readme、handoff 交接文档、MOC 总索引文档、维护指南**（以及其他同类索引/说明类文档）。
- 必须明确说明：**哪几份没有改动、为什么没有改动**，不能只给一句笼统的"文档已更新"。
- 必须给出足够的**对账结果**（逐条对应：改了什么、对应哪份文档的哪一节、未改的是否确认无需改），可回溯、可核查。
- 这是需要长期维护的工作，在项目中极其重要，不可省略。
- 新增分册必须补其与 00~13 及关键 ADR 的交叉格；缺格视为未对账。
- 无依据行的 ✓ 视为未核对，按未对账处理。

## 版本管理与历史留存

- 项目采用 Git 单一仓库（monorepo）：文档、脚本、JSON、代码同仓管理，确保同一次提交内"文档与实现"处于同一版本，天然满足对齐要求。
- **单 Agent 顺序作业时直推 main**；多 Agent 并行时必须按 [13 册](13-concurrency-and-lifecycle.md) 认领，必要时开分支，禁止对同一文件并行直推。分支落地前须完成审查（含引用矩阵与审查结论），合并历史即"三件套审计"的存档。
- 口径版本用 tag 标记（如 `prd-v1.2`）；交接文档中引用 tag 与 commit，不靠口头描述。
- 回滚即版本操作：改错了用 revert 或切回指定 commit，历史资料永久可追溯、可拉取恢复。
- 仓库为唯一权威副本（remote 与本地镜像并行），本地不留未入库的"临时最终版"。
- 敏感信息不入库：真实财税数据须脱敏，密钥、Token、本地配置一律不提交；凭据类信息不写入本记忆文件，也不写进任何会提交的文档。

## 脱敏判定标准（2026-11-23，[ADR-026](../docs/adr/ADR-026-nine-item-rulings-deadline-desensitization.md)）

> 适用：入库文件、交付正文、外部 Agent 回传候选、测试数据与报告；本条解决"什么叫脱敏"此前只有原则、无判定标准的问题。

- **必删类别（出现即须替换，不得保留原值）**：① 身份证、护照、军官证等证件号；② 手机号、固定电话、邮箱、即时通讯账号；③ 银行账号、支付账号、卡号；④ 纳税人识别号、统一社会信用代码；⑤ 自然人姓名及客户/供应商/项目等可反查主体的名称；⑥ 门牌级地址、精确金额（业务金额只留区间或比例）、内部基础设施标识（主机名、内网 IP、服务器/共享盘绝对路径、内部系统名；不含公开仓库相对路径与示例路径）。
- **可保留类别**：日期（必要时粗化到月）、岗位/角色、业务场景与偏好语义、统计量与比例、政策名称与条款号。
- **替换约定**：统一使用固定占位符 `<姓名>`、`<手机号>`、`<证件号>`、`<账号>`、`<纳税人识别号>`、`<金额>`、`<项目名>`、`<地址>`、`<路径>`；同一文件内同一实体只用一种占位符，禁止一处真值一处占位。
- **判定三问（任一不通过即未脱敏）**：① 去掉该字段后结论是否仍成立？② 该字段能否单独或结合公开信息定位到具体主体？③ 是否已按固定占位符替换且全文件一致？
- **机械辅助（先告警后阻断）**：`scripts/secrets_scan.sh` 对证件号与手机号做告警扫描（2026-11-23 实测本库两类模式零命中）；未完成真实回归与第二平台实跑前只告警、不阻断（[rules/10](10-lessons.md)）。该扫描挂在主会话 pre-commit，只覆盖被改文件；外部 Agent 按 S-007 手工跑同等检查。机械只能兜底高精度模式，语义级脱敏仍按三问人工判定。
- **外部 Agent 回传候选**：按本节执行，候选不得含原话与可识别要素；主会话收口入册前按本节复核（[ADR-024](../docs/adr/ADR-024-external-agent-instruction-observation.md)）。

## ADR 取代流程（旧结论被推翻时）

- **不得静默修改**旧 ADR，按四步走：
  1. **新建 ADR**：写明取代哪一份 ADR 的哪些条款，并给出新结论。
  2. **旧 ADR 顶部标注**：加 `> 已被 ADR-xxx 取代（YYYY-MM-DD，限<条款>）`。
  3. **INDEX 改状态**：`docs/adr/INDEX.md` 改为「部分被取代」或「已取代」。
  4. **新 ADR 写「可推翻条件」**：不写视为未完成。
- 示例（3 行）：ADR-007 写「取代 ADR-004 第 1 条 150 行阈值」；ADR-004 顶部标「已被 ADR-007 取代（阈值条款）」；INDEX 中 ADR-004 状态改「部分被取代」。

## 提交与推送的固定步骤（缺一步即未完成）

0. 先跑 `scripts/context_budget.sh`（pre-commit 已自动执行，手工核对时需单跑）；
1. `git add` 本轮改动 → 提交（pre-commit 自动跑 `md_check.sh` + `link_check.sh` + `context_budget.sh` + 生成交付草稿，任一失败即禁止提交）；
2. `git push origin main`（pre-push 自动做凭据自检与密钥恢复）；
3. 核对 `git status -sb` 显示分支与 `origin/main` 齐平，即 **ahead 0**；
4. 核对远端哈希：`git rev-parse HEAD` 与 `git ls-remote origin main` 的值一致；
5. 把以上实际输出粘贴进交付回复（D-5），不得只写"已推送"。
