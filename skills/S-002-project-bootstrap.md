- **名称**：项目初始化与骨架验收（project bootstrap）
- **编号**：S-002
- **适用场景**：已有冻结的 PRD、要把项目从零建到"一条命令跑通最薄端到端路径"时；需求尚未收集时先用 [S-003](S-003-requirements-intake.md)
- **前置输入**：冻结并打过 tag 的 PRD；已判定的项目级别（脚本工具型／单机应用型／内网服务型）；已定边界见 [rules/14](../rules/14-project-bootstrap.md)
- **步骤**：
  1. 定级：按"有无 UI、是否常驻、是否多用户"定级并写 ADR；A7、A8 不可裁；裁其余步骤须由非起草者的独立审查者签字（理由、风险、补偿动作），裁 A5 还须同步改写 A7 判定口径，否则不得裁。
  2. A1 可执行化检查：逐张 RQ 核对验收标准与失败条件，缺项打回需求方。
  3. A2 写初始化 ADR：约束、选型、否决项及原因、可推翻条件四栏齐全（格式按 [06](../rules/06-quality.md)）。
  4. A3 技术栈：为每个选型标出对应的约束原文与出处，追不到约束的删掉。
  5. A4 目录契约：固定骨架，逐目录写一句职责；不设 `misc/`、`utils/` 类杂项目录。
  6. A5 环境可复现：锁定解释器与依赖版本，提供 `.env.example`，README 写"5 分钟上手"命令。
  7. A6 依赖与许可证：最小依赖、版本锁定，剔除 GPL/AGPL 类传染性许可。
  8. A7 门禁（不可裁）：格式化、lint、测试、pre-commit、CI 串成一条命令，失败即阻断。
  9. A8 骨架（不可裁）：跑通"页面 → 后端 → 数据库 → 回显"一条命令，留存输出与日志。
- **判定标准（验收）**：
  - 干净环境照 README 在 5 分钟内跑通，且不改任何代码或配置；
  - 门禁一条命令可复现失败，不是"人工记得跑"；
  - 每个选型都能指到一条约束，ADR 四栏无空缺；
  - A8 的端到端输出已留存；仅"能启动"不算通过。
- **触发词**：「帮我从零把这个项目搭起来」「有 PRD 了，开始建项目」「新项目目录结构该怎么定」「初始化项目要准备什么」「怎么保证新项目能一条命令跑通」「项目骨架验收标准」「新项目选型怎么定」「从零建到能运行」
- **不适用**：① 需求还没冻结、只有口头想法 → 改走 [S-003](S-003-requirements-intake.md)；② PRD 已冻结、要派子 Agent 撰写 → 改走 [S-001](S-001-subagent-dispatch.md)；③ 只是接入规则库、确认规则是否生效 → 改走 [S-004](S-004-rulebase-onboarding.md)
- **完成判据**：照 README 在干净环境跑通且不改代码配置；门禁一条命令可复现失败；A8 端到端输出与日志已留存；初始化 ADR 四栏无空缺（格式见 `rules/06-quality.md`）。
- **单一来源**：项目定级、A1~A8 与边界见 `rules/14-project-bootstrap.md`，选型决策格式见 `rules/06-quality.md`，阈值与预算见 `scripts/budget.conf`（本文不复述）。
- **常见坑**：先写代码后补 ADR，导致选型无约束来源；目录里塞 `utils/` 变成第二垃圾场；测试数据未脱敏就入库；把"能启动"当成骨架跑通；为图快引入默认开启遥测的依赖；起草者自签裁剪意见、或裁掉 A7/A8 省事。
- **来源**：2026-11-18 用户批准新增"项目创建与需求收集"规则时沉淀；配套 [W-001](../workflows/W-001-new-project.md)
- **版本**：v1.0
