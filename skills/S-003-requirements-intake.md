- **名称**：需求收集与 PRD 冻结（requirements intake）
- **编号**：S-003
- **适用场景**：用户提出新项目或新功能但没有需求文档，只有口头描述、零散表格或旧系统截图时；产出冻结 PRD 后交 [S-002](S-002-project-bootstrap.md) 建项目
- **前置输入**：用户对用途、使用者、数据来源、合规要求的初步描述；已定边界见 [rules/14](../rules/14-project-bootstrap.md)
- **步骤**：
  1. R1 问边界：一次问清谁用、解决什么问题、数据从哪来、合规红线、明确不做什么；技术问题自己定。
  2. R2 建卡：按 [templates/RQ-CARD.md](../templates/RQ-CARD.md) 一条需求一张卡，编号 `RQ-001` 起连续递增。
  3. 每个必答项标出处（用户原话+日期，或需求文档 `文件:行号`）与状态（用户已确认／待确认／Agent 假设）；**无出处即未确认，不得写入 PRD**。补全输入、输出、验收标准、例外与失败处理、优先级。
  4. R3 核口径：财税条目写政策名称 + 条款 + 核实状态；"待确认"项登记到期日，到期仍核不实的二选一——移出本期，或用户书面确认承接风险后带"未核实"标记开发（[05](../rules/05-requirement-review.md)）。禁止静默带病推进。
  5. R4 派单：主 Agent 整理卡片后按 [S-001](S-001-subagent-dispatch.md) 派子 Agent 写 PRD。
  6. 建"卡片↔PRD 条款"引用矩阵，双向逐条核对；断链退回子 Agent，主 Agent 不代写。
  7. R5 请用户确认：清单只列业务口径与优先级，技术项不得上单。
  8. R6 冻结：按 [08](../rules/08-alignment-and-versioning.md) 打 tag（如 `prd-v0.1`）；用户当轮明确指令优先（[13](../rules/13-concurrency-and-lifecycle.md)），但当轮之后必须补变更单，未补登记视为未发生。
- **判定标准（验收）**：
  - 每张卡五栏边界无空缺，每个必答项都有出处与状态，无出处的项未进入 PRD；
  - 引用矩阵双向无断链，每张 RQ 与每条 PRD 条款一一可追；
  - 无"待确认"状态的政策依据混入 PRD；待确认项均有到期日，超期已按"移出本期/书面承接"处置；
  - 冻结后有 tag，变更单可查到影响面与受影响条款；口头指令均已补登记。
- **常见坑**：跳过 R1 直接写 PRD，返工在开发阶段；把"待确认"写成"已核实"；用 Agent 假设填满空缺当作用户结论；待确认项无到期日导致项目停摆；主 Agent 替子 Agent 写 PRD 再做审查（自己审自己）；口头加需求未落变更单。
- **来源**：2026-11-18 用户批准新增"项目创建与需求收集"规则时沉淀；配套 [W-001](../workflows/W-001-new-project.md)
